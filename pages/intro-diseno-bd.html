Curso de Diseño de Bases de Datos

¿Qué es el diseño de bases de datos?

Leer explicación

El diseño de una base de datos es el proceso de organizar, estructurar y modelar los datos de un sistema de información para que puedan almacenarse, consultarse, actualizarse y eliminarse de forma eficiente, evitando redundancia y asegurando consistencia.

  • Se centra en identificar:
    • Entidades: objetos o conceptos del sistema.
    • Atributos: sus características.
    • Relaciones: cómo se conectan entre sí.
  • Implica aplicar principios como la normalización, para optimizar la estructura y hacerla escalable.
  • El objetivo principal es representar la información del mundo real de forma clara, lógica y útil dentro de un sistema gestor de bases de datos.

¿Por qué es importante el diseño de bases de datos?

Leer explicación

Un buen diseño de base de datos evita problemas como duplicidad de información, errores de integridad y dificultades en las consultas. Además, facilita la escalabilidad y el mantenimiento del sistema.

  1. Reduce redundancias de datos.
  2. Asegura integridad y consistencia.
  3. Mejora el rendimiento de las consultas.
  4. Facilita actualizaciones y mantenimiento.

¿Qué es el modelo relacional (SQL)?

Leer explicación

SQL (Structured Query Language)

Definición:
SQL es un lenguaje estándar para gestionar y manipular bases de datos relacionales. Permite organizar los datos en tablas con filas y columnas y seguir un esquema bien definido que establece cómo deben organizarse. Con SQL se pueden realizar operaciones como consultas, inserciones, actualizaciones y eliminaciones de datos.

Características principales:

  1. Modelo relacional: Trabaja con tablas, filas y columnas.
  2. Esquema fijo: La estructura de los datos debe estar predefinida.
  3. Operaciones estándar: Permite crear, leer, actualizar y eliminar datos.
  4. Lenguaje universal: SQL es usado en la mayoría de los sistemas de gestión de bases de datos relacionales (RDBMS).
  5. Consultas complejas: Permite unir tablas, filtrar, agrupar y ordenar información.

¿Qué es el modelo no relacional(NoSQL)?

Leer explicación

NoSQL (Not Only SQL)

Definición:
NoSQL es un término para las bases de datos no relacionales que no siguen la estructura de tablas con filas y columnas del modelo relacional. Permite almacenar datos no estructurados o semi-estructurados y ofrece mayor flexibilidad y escalabilidad en comparación con SQL.

Características principales:

  1. Flexibilidad de esquema: No requiere una estructura fija; los registros pueden tener diferentes campos.
  2. Alto rendimiento: Optimizado para grandes volúmenes de datos y operaciones rápidas de lectura y escritura.
  3. Escalabilidad horizontal: Se puede aumentar la capacidad agregando más servidores.
  4. Variedad de modelos:
    1. Documental: Datos en documentos JSON o BSON (ej. MongoDB).
    2. Clave-valor: Pares clave-valor (ej. Redis).
    3. Columnar: Optimizado para grandes datasets y consultas analíticas (ej. Cassandra).
    4. Grafos: Para relaciones complejas entre entidades (ej. Neo4j).
  5. Adaptabilidad: Ideal para datos en constante cambio o provenientes de múltiples fuentes.

Cuándo usar SQL (Bases de datos relacionales)

Leer explicación
  1. Estructura de datos bien definida:
    • Los datos tienen una estructura fija (tablas con columnas y tipos de datos definidos).
    • Se requiere un esquema rígido que no cambie con frecuencia.
  2. Relaciones complejas entre datos:
    • Hay muchas relaciones entre tablas, como en sistemas de gestión empresarial o CRM.
    • Se necesita realizar consultas que integren múltiples tablas (joins).
  3. Integridad y consistencia de datos:
    • Es fundamental garantizar la consistencia y precisión de los datos (por ejemplo, en transacciones bancarias).
    • Necesitas soporte para transacciones ACID (Atomicidad, Consistencia, Aislamiento, Durabilidad).
  4. Consultas avanzadas:
    • Requieres consultas SQL complejas con agrupaciones, filtros o cálculos avanzados.
    • La base de datos se usa para analítica detallada o reportes.
  5. Escalabilidad vertical:
    • Prefieres escalar en potencia (mejorar el hardware del servidor) en lugar de distribuir los datos horizontalmente.
  6. Ejemplos de casos de uso:
    • Sistemas financieros y bancarios.
    • Sistemas de gestión de inventario.
    • Sistemas de comercio electrónico con relaciones complejas entre productos, clientes y pedidos.

¿Cuándo usar NoSQL (Bases de datos no relacionales)?

Leer explicación
  1. Flexibilidad en la estructura de datos:
    • Los datos no tienen una estructura fija o cambian con frecuencia (por ejemplo, documentos JSON, claves-valor).
    • La aplicación evoluciona rápido y necesita un modelo de datos adaptable.
  2. Grandes volúmenes de datos:
    • Manejas datos masivos que no caben fácilmente en un solo servidor (Big Data).
    • Necesitas escalar horizontalmente (añadir más servidores para repartir la carga).
  3. Alta velocidad de escritura y lectura:
    • Requieres almacenar y recuperar datos rápidamente (baja latencia).
    • Es común en aplicaciones en tiempo real, como redes sociales o sistemas de recomendaciones.
  4. Independencia de relaciones:
    • Los datos tienen pocas o ninguna relación entre sí.
    • Cada dato puede ser tratado de manera independiente.
  5. Escalabilidad horizontal:
    • Prefieres distribuir los datos entre múltiples servidores o nodos.
    • Necesitas manejar picos de tráfico sin comprometer el rendimiento.
  6. Ejemplos de modelos NoSQL:
    • Documentos (MongoDB): Ideal para datos semiestructurados como JSON.
    • Clave-valor (Redis, DynamoDB): Para datos simples como sesiones de usuario.
    • Grafos (Neo4j): Para analizar relaciones complejas (redes sociales).
    • Columnas (Cassandra): Para consultas rápidas en grandes volúmenes de datos.
  7. Ejemplos de casos de uso:
    • Aplicaciones móviles o web de alta carga (Facebook, Twitter).
    • Sistemas de análisis en tiempo real.
    • Almacenamiento de logs y datos de IoT.
    • Catálogos de productos en constante cambio.

¿Qué son los gestores de bases de datos?

Leer explicación

Un gestor de bases de datos o DBMS (Database Management System) es un software que permite crear, organizar, consultar y mantener bases de datos de manera eficiente. Su función principal es garantizar la integridad, seguridad y consistencia de los datos, además de facilitar su acceso y manipulación.

Gestores de bases de datos para SQL

Los gestores SQL están diseñados para bases de datos relacionales, donde los datos se organizan en tablas con un esquema definido. Permiten realizar consultas complejas y mantener la consistencia de los datos mediante transacciones ACID.

  • MySQL: Muy usado en aplicaciones web, fácil de implementar.
  • PostgreSQL: Avanzado, soporta transacciones complejas y análisis de datos.
  • Oracle Database: Usado en entornos corporativos y sistemas críticos.
  • Microsoft SQL Server: Integración con entornos Windows y aplicaciones empresariales.

Gestores de bases de datos para NoSQL

Los gestores NoSQL están diseñados para bases de datos no relacionales, con esquemas flexibles y escalabilidad horizontal. Son ideales para grandes volúmenes de datos, aplicaciones en tiempo real y datos semiestructurados.

  • MongoDB: Basado en documentos JSON, ideal para datos semiestructurados y aplicaciones web rápidas.
  • Redis: Almacenamiento clave-valor en memoria, muy rápido para datos temporales.
  • Cassandra: Columnar, optimizado para grandes volúmenes de datos distribuidos.
  • Neo4j: Orientado a grafos, ideal para analizar relaciones complejas como redes sociales.

Leer explicación

Una entidad representa un objeto del mundo real sobre el cual se almacena información en una base de datos. En SQL, una entidad se modela como una tabla, y sus características se representan mediante atributos (columnas).

¿Qué significa CRUD?

Leer explicación

CRUD significa Crear (Create), Leer (Read), Actualizar (Update) y Eliminar (Delete). Representa las cuatro operaciones básicas realizadas en una base de datos o sistema de almacenamiento:

  1. Crear (Create): Agregar nuevos datos, como insertar un registro nuevo.
  2. Leer (Read): Recuperar o consultar datos existentes.
  3. Actualizar (Update): Modificar datos existentes.
  4. Eliminar (Delete): Borrar datos.

¿Qué es la lógica del negocio?

Leer explicación

Es el conjunto de reglas y validaciones de datos importantes para el negocio. La lógica de negocio es el conjunto de reglas, procesos y validaciones que definen y regulan cómo opera un negocio. Es la capa que traduce las políticas y objetivos empresariales en procedimientos concretos, determinando cómo se deben manipular, transformar y validar los datos para cumplir con los requerimientos y flujos de trabajo propios de la organización.

¿Qué son las relaciones?

Leer explicación

Un modelo relacional se define cuando las tablas están vinculadas entre sí mediante claves primarias (PK) y claves foráneas (FK), permitiendo establecer relaciones como uno a muchos (1:M), muchos a muchos (M:M) o uno a uno (1:1).

📌 Tipos de Relaciones en SQL

  • 1 a 1 (Uno a Uno) 🔗: Una fila de una tabla está relacionada con una sola fila en otra tabla.
  • 1 a M (Uno a Muchos) 🔗➡️: Una fila de una tabla puede estar relacionada con varias filas en otra tabla.
  • M a M (Muchos a Muchos) 🔗🔗: Múltiples filas de una tabla pueden estar relacionadas con múltiples filas de otra. Se gestiona con una tabla intermedia.

¿Qué es la cardinalidad?

Leer explicación

La cardinalidad describe la relación entre los registros de dos tablas, indicando cuántos registros de una tabla pueden estar asociados con registros de otra.

Tipos comunes:

  • 1:1 (Uno a Uno): Ejemplo: Un usuario tiene un único número de pasaporte.
  • 1:N (Uno a Muchos): Ejemplo: Un autor puede escribir varios libros.
  • N:M (Muchos a Muchos): Ejemplo: Una película tiene varios actores y un actor puede participar en varias películas.

¿Qué son las llaves?

Leer explicación

En el diseño de bases de datos, las claves son atributos que permiten garantizar la integridad y unicidad de los datos:

  • Clave Primaria (PK): Identifica de manera única cada registro en una tabla. No puede contener valores nulos ni repetidos.
  • Clave Foránea (FK): Atributo que referencia la clave primaria de otra tabla, estableciendo relaciones e integridad referencial.
  • Clave Única (Unique Key): Garantiza que los valores sean únicos en la columna, pero permite valores nulos. Ejemplo: el correo electrónico en una tabla de usuarios.

¿Cuáles son las diferencias entre relaciones y cardinalidad?

Leer explicación
  • Relaciones: Son el enlace entre dos tablas usando PK y FK. Ejemplo: La tabla Clientes tiene id_cliente como PK, y la tabla Ventas guarda ese mismo id_cliente como FK.
  • Cardinalidad: Explica cuántos registros de una tabla pueden relacionarse con otra. Ejemplo: Un cliente puede tener muchas ventas (1:N), pero cada venta solo pertenece a un cliente.

Metáfora para entenderlo fácil

Piensa en Clientes como los padres y en Ventas como los hijos.

La relación es el vínculo padre-hijo: el apellido que conecta a los hijos con su padre.

La cardinalidad indica la cantidad: un padre puede tener muchos hijos (1:N), pero cada hijo solo tiene un padre (N:1).

¿Qué es la normalización en bases de datos?

Leer explicación

La normalización se aplica tanto en el rediseño de bases de datos existentes como en el modelado desde cero. Es un proceso estructurado que optimiza la organización de los datos, minimiza la redundancia y mejora la integridad. Su objetivo principal es descomponer una base de datos grande en tablas más pequeñas y bien definidas, asegurando relaciones lógicas y eficientes entre los datos.

1. Primera Forma Normal (1NF)

Requisitos:

  • Eliminar grupos repetitivos de columnas.
  • Cada columna debe contener valores atómicos (indivisibles).

Problema: Tabla Clientes con teléfonos múltiples en una misma celda:

Clientes (Sin Normalizar)
IDNombreTeléfono
1Ana12345
2Luis67890
3Marta23456, 34567

Solución: Dividir los teléfonos en registros individuales.

Clientes (Normalizada 1NF)
IDNombreTeléfono
1Ana12345
2Luis67890
3Marta23456
3Marta34567

Beneficios:

  • Elimina valores repetidos en la misma celda.
  • Facilita búsquedas y consultas.
  • Permite establecer relaciones con otras tablas.
  • Evita problemas de integridad.

2. Segunda Forma Normal (2NF)

Requisitos:

  • Cumplir con 1NF.
  • Eliminar dependencias parciales: cada columna no clave depende de toda la clave primaria.
  • Eliminar redundancia y asegurar que cada dato depende únicamente de la clave primaria.

Rediseño de bases de datos existentes: ejemplo práctico

Leer explicación

El rediseño de bases de datos existentes implica analizar la estructura actual y aplicar mejoras para optimizar el almacenamiento y la integridad de los datos. En este caso, el rediseño consistirá en aplicar normalización para eliminar redundancias y mejorar la consistencia.

¿Qué representa el gráfico?

El gráfico principal muestra una tabla combinada con información de ventas, clientes, productos, direcciones y países. Aunque es útil para visualizar todo en una sola vista, no está normalizado, lo que genera redundancia y posibles inconsistencias.

¿Cómo se normalizó la base de datos?

Se aplicaron los principios de normalización en tres pasos principales:

  • Paso 1: Primera Forma Normal (1NF)

    Se identificaron entidades distintas y se separaron en tablas individuales:

    • Cliente: nombre, apellido, correo, teléfono.
    • Producto: nombre, precio.
    • Dirección: calle, número, ciudad, país.
    • País: nombre, dominio.
    • Venta: fecha, cliente, dirección, producto, cantidad.

    Esto eliminó los grupos repetidos y garantizó que cada campo contuviera valores atómicos.

  • Paso 2: Segunda Forma Normal (2NF)

    Se eliminaron dependencias parciales. Por ejemplo:

    • El nombre del cliente no depende de la venta, sino del ID del cliente.
    • La dirección y el producto también se referencian por ID.

    La tabla Venta quedó con claves foráneas que apuntan a otras tablas.

  • Paso 3: Tercera Forma Normal (3NF)

    Se eliminaron dependencias transitivas. Por ejemplo:

    • El país no se repite en cada dirección, sino que se referencia desde la tabla País.

    Esto evita redundancia y facilita actualizaciones consistentes.

Resultado: Una base de datos estructurada, eficiente y sin redundancias, donde cada tabla representa una entidad única y se relaciona mediante claves primarias y foráneas.

Modelado de datos desde 0 - Versión borrador Inicial

Leer explicación

Tarea

Diseña desde cero el modelo de datos para un sistema de ventas siguiendo los pasos explicados en la guía. La tarea consiste en:

  1. Identificar las entidades del sistema.
  2. Identificar los atributos de las entidades.
  3. Identificar las llaves primarias (PK) y foráneas (FK).
  4. Asignar una nomenclatura adecuada a las entidades y sus atributos.
  5. Identificar las entidades pivote (EP) del sistema.
  6. Identificar los catálogos (EC) del sistema.
  7. Identificar los tipos de relaciones del sistema.
  8. Crear el Modelo Entidad-Relación del sistema.
  9. Crear el Modelo Relacional de la base de datos del sistema.
  10. Identificar los tipos de dato de los atributos de las entidades del sistema.
  11. Identificar los atributos únicos (UQ) en el sistema.
  12. Identificar las reglas de negocio (operaciones CRUD) del sistema.

Análisis de los Pasos y su Aplicación en un Sistema de Ventas (Borrador Inicial)

Nota: Esta guía detalla el proceso paso a paso para facilitar la comprensión.
A medida que adquieras más experiencia, podrás omitir este nivel de detalle y trabajar directamente con la versión final del documento.

1. Identificar las entidades del sistema

  • Clientes (quién compra)
  • categorías_productos (clasificación o grupo al que pertenece cada producto)
  • Productos (qué se vende)
  • formas_pago (métodos de pago disponibles)
  • Ventas (registro de compras)
  • Detalles de Venta (relación entre Ventas y Productos)

2. Identificar los atributos de las entidades

  • Clientes: nombre
  • Productos: nombre, precio, stock
  • Ventas: fecha
  • Detalles_de_Venta: cantidad, precio_unitario

3. Identificar las llaves primarias y foráneas

  • Claves primarias (PK):
    • Clientes: id_cliente
    • Categorías_productos: id_categoria
    • Productos: id_producto
    • Formas_pago: id_forma_pago
    • Ventas: id_venta
    • Detalles_de_Venta: id_detalle
  • Claves foráneas (FK):
    • Clientes: No tiene
    • Categorías_productos: No tiene
    • Productos: id_categoria
    • Formas_pago: No tiene
    • Ventas: id_cliente, id_forma_pago
    • Detalles_de_Venta: id_venta, id_producto

4. Asignar una nomenclatura adecuada a las entidades y sus atributos

  • Nombres descriptivos y específicos:
    • Incorrecto: id
    • Correcto: id_cliente, id_producto, id_venta
  • Uso de snake_case para nombres compuestos:
    • Incorrecto: IdCliente, idCliente, id-cliente
    • Correcto: id_cliente, fecha_venta, precio_total
  • Prefijo id_ para claves primarias:
    • Siempre usar id_ seguido del nombre de la entidad
  • Nombres en plural para entidades:
    • Incorrecto: cliente, producto, venta
    • Correcto: clientes, productos, ventas
  • Consistencia en las claves foráneas:
    • En la tabla venta, la FK debe llamarse id_cliente, no cliente_id
    • En la tabla producto, la FK debe llamarse id_categoria, no categoriaID
  • Evitar palabras reservadas y caracteres especiales:
    • Incorrecto: order, user-name
    • Correcto: orden, nombre_usuario

5. Identificar las entidades pivote del sistema

  • Son tablas intermedias que unen otras entidades
  • Detalles de Venta es la pivote, ya que relaciona Ventas con Productos

6. Identificar los catálogos del sistema

  • Categorías de productos (Celulares, Accesorios, Tablets)
  • Formas de pago (Efectivo, Tarjeta de crédito, Transferencia bancaria)

7. Identificar los tipos de relaciones del sistema

  • Un Cliente puede realizar muchas Ventas → (1:M) → clientes.id_cliente → ventas.id_cliente
  • Una Categoría de Producto puede tener muchos Productos → (1:M) → categorías_productos.id_categoria → productos.id_categoria
  • Un Producto pertenece a una sola Categoría de Producto → (M:1) → productos.id_categoria → categorías_productos.id_categoria
  • Una Venta puede tener muchos Detalles de Venta → (1:M) → ventas.id_venta → detalles_venta.id_venta
  • Un Detalle de Venta está asociado a un solo Producto → (M:1) → detalles_venta.id_producto → productos.id_producto
  • Un Producto puede aparecer en muchos Detalles de Venta → (1:M) → productos.id_producto → detalles_venta.id_producto
  • Un Cliente utiliza una sola Forma de Pago por Venta → (M:1) → ventas.id_forma_pago → formas_pago.id_forma_pago
  • Una Forma de Pago puede ser utilizada en muchas Ventas → (1:M) → formas_pago.id_forma_pago → ventas.id_forma_pago
  • Para manejar la relación N:M entre Ventas y Productos, se usa Detalles de Venta

8. Crear el Modelo Entidad-Relación del sistema

El Modelo Entidad-Relación (MER) permite visualizar las relaciones entre las entidades del sistema mediante diagramas. Puedes usar herramientas como:

  • MySQL Workbench
  • Lucidchart
  • Draw.io

9. Crear el Modelo Relacional de la base de datos del sistema

Este es el diseño definitivo en SQL, listo para implementarse. Investigar y aprender sobre modelado Entidad-Relación es recomendable para estructuras más eficientes.

10. Identificar los tipos de dato de los atributos de las entidades

  • Cadenas de texto: VARCHAR(100)
  • Números enteros: INT
  • Números decimales: DECIMAL(10,2)
  • Fechas: DATE

11. Identificar los atributos únicos en el sistema

  • Clientes: email, telefono
  • categorías_productos: nombre_categoria
  • formas_pago: descripcion

12. Identificar las reglas de negocio (Operaciones CRUD)

  • Clientes:
    • Create: Agregar nuevos clientes
    • Read: Consultar clientes registrados
    • Update: Modificar datos de contacto
    • Delete: Eliminar clientes según restricciones
  • Productos:
    • Create: Añadir productos al catálogo
    • Read: Ver lista de productos disponibles
    • Update: Modificar precios y stock
    • Delete: Eliminar productos descontinuados
  • Ventas:
    • Create: Registrar una venta
    • Read: Consultar historial de ventas
    • Update: Corregir errores
    • Delete: Cancelar ventas bajo ciertas condiciones

Ejemplo de Caso Real: Juan compra:

  • 1 celular ($500)
  • 2 fundas ($10 cada una)

Registro en el sistema:

  • Venta #1 asociada a Juan
  • Detalles de Venta:
    • Producto: Celular, Cantidad: 1, Precio: $500
    • Producto: Funda, Cantidad: 2, Precio: $10 cada una

Con esta estructura, la tienda puede consultar historial de compras, ver qué productos tienen más demanda y controlar stock y reposiciones.

Modelado de datos desde 0 – Versión final del documento

Leer explicación

El diseño de esta base de datos se desarrolló desde cero con el objetivo de estructurar un sistema de ventas eficiente y coherente. Inicialmente se identificaron problemas clave en la gestión de información, tales como la duplicación de datos, inconsistencias en el registro de clientes, productos y ventas, y la dificultad para relacionar correctamente las transacciones con los elementos involucrados. Para resolver estas problemáticas, se aplicó un proceso de modelado estructurado que incluyó la identificación de entidades, la definición de atributos clave, la asignación de claves primarias y foráneas y la determinación de las relaciones entre las tablas.

Relaciones

  • Un cliente genera ventas (1 - N).
  • Una venta tiene detalles de venta (1 - N).
  • Un detalle de venta pertenece a un producto (N - 1).
